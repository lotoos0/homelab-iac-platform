# Test VM boots but does not receive a DHCP lease

> **Status:** Paused - superseded by platform architecture change
> **Related issue:** #9
> **Date:** 2026-08-24

## What happened

The first disposable Debian 13 VM was created to validate the `homelab-iac` libvirt network.

The VM starts successfully, but no DHCP lease appears on the libvirt network.

At this point I know the VM exists and the host-side bridge is alive. What I do not know yet is whether the guest actually sends a DHCP request, or whether the request reaches the libvirt DHCP service.

## Expected behavior

After boot, the VM should:

1. attach to the `homelab-iac` network,
2. request an IPv4 address using DHCP,
3. receive an address from `10.50.0.100-10.50.0.200`,
4. use `10.50.0.1` as the network gateway.

## Observed behavior

The VM is running:

```text
test-vm   running
```

The VM interface is attached to the expected libvirt network:

```text
Interface: vnet1
Type:      network
Source:    homelab-iac
Model:     virtio
```

The host bridge changed from the earlier `NO-CARRIER` state to:

```text
virbr50: UP, LOWER_UP
IPv4: 10.50.0.1/24
```

This confirms that a guest interface is now attached to the bridge.

However:

```bash
virsh -c qemu:///system net-dhcp-leases homelab-iac
```

returns no leases.

The libvirt-managed `dnsmasq` process for the network is also running:

```text
/usr/sbin/dnsmasq --conf-file=/var/lib/libvirt/dnsmasq/homelab-iac.conf
```

This confirms that the service process exists, but not that DHCP requests reach it.

### DHCP packet capture

DHCP traffic was captured directly on `virbr50` while the test VM was being restarted:

```bash
sudo timeout 40 tcpdump -ni virbr50 -e -vv 'udp port 67 or udp port 68'
```

The capture returned:

```text
0 packets captured
0 packets received by filter
0 packets dropped by kernel
```

No DHCP traffic was observed on the bridge. This moved the investigation closer to the guest side and led to a capture directly on the VM tap interface.

### Guest interface capture

All traffic was captured directly on the VM tap interface:

```bash
sudo timeout 30 tcpdump -ni vnet1 -e -vv
```

The capture contained only STP frames generated by the host bridge.

No DHCP, ARP, IPv6 neighbor discovery or other obvious guest-originated traffic was observed.

This is important because it moves the investigation away from the libvirt DHCP service. The host-side bridge is active and traffic reaches the VM tap interface, but the guest does not appear to transmit normal network traffic.

The next step is to verify whether the Debian guest actually completes its boot.

### Guest boot investigation

The VM remained in the `running` state and QEMU CPU counters continued to increase, so the virtual machine process itself was active.

The QEMU log confirmed that the expected devices were created:

- qcow2 overlay with the Debian base image
- virtio block device
- virtio network interface
- serial console
- QEMU guest agent channel

No obvious QEMU-level startup error was present.

However, the serial console stopped after:

```text
Booting `Debian GNU/Linux`
```

and the guest still produced no DHCP, ARP or other normal network traffic.

At this point it is not yet clear whether the guest OS completes the boot or whether the issue happens before userspace networking starts.

## What this already tells me

The problem is probably not simply "the VM has no network interface".

The following pieces are already present:

- VM is running
- virtio NIC exists
- NIC is connected to `homelab-iac`
- guest tap interface `vnet1` exists
- `virbr50` is operational and has carrier
- gateway address `10.50.0.1/24` is present

The failure is somewhere further along the DHCP path.

## Current hypotheses

These are hypotheses, not conclusions yet.

1. Debian did not bring the guest interface up.
2. The guest did not start or complete a DHCP request.
3. The DHCP request does not reach libvirt/dnsmasq.
4. libvirt/dnsmasq receives the request but does not answer.
5. Guest initialization or cloud-init has affected network configuration.

## Hypothesis: genericcloud image compatibility

**Status:** Deprioritized

A known compatibility problem exists around Debian `genericcloud`, Q35 and cloud-init media ([Debian bug #992119](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=992119), [Debian bug #1104426](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1104426)), so the same test was repeated with the larger Debian `generic` image.

The replacement image did not solve the problem:

- the VM did not remain running
- no DHCP lease appeared

Because the failure persisted after changing only the image variant, `genericcloud` itself is unlikely to be the sole root cause of this incident. The VM state did change, however: the earlier `genericcloud` test remained in the `running` state, while the `generic` test did not.

The investigation returns to the guest boot process.

## Finding 1 - VM lifecycle

**Status:** Confirmed

The VM was previously terminated by libvirt shortly after startup.

Adding:

```text
--wait 2
```

kept the VM running long enough for the guest to continue booting.

This explains the earlier immediate shutdown, but it does not explain the missing DHCP lease.

## Finding 2 - DHCP

**Status:** Investigating

With the VM now remaining in the `running` state, the libvirt DHCP lease table is still empty.

The missing lease is independent from the earlier libvirt lifecycle issue. It was first observed alongside the guest reboot loop, but the later TCG comparison also produced no lease without repeated reboot events. DHCP therefore remains a separate open question.

### Host TAP traffic vs guest traffic

The initial capture on `vnet4` showed IPv6 and STP traffic, but the source MAC required a closer look.

The guest NIC uses:

```text
52:54:00:a0:78:ef
```

while the host-side TAP interface uses:

```text
fe:54:00:a0:78:ef
```

`ip addr show vnet4` confirmed:

```text
vnet4
link/ether fe:54:00:a0:78:ef
inet6 fe80::fc54:ff:fea0:78ef/64
```

The previously observed STP, IPv6 router solicitation and mDNS traffic therefore originated from the host-side TAP interface, not from the Debian guest.

The next capture filtered specifically for frames using the guest MAC as the source.

### Guest-only traffic capture

To remove host-side TAP traffic from the capture, traffic was filtered using the actual guest MAC address:

```bash
sudo timeout 40 tcpdump -ni vnet4 -e -vv \
  'ether src 52:54:00:a0:78:ef'
```

The VM was reset while the capture was running.

The capture returned:

```text
0 packets captured
0 packets received by filter
0 packets dropped by kernel
```

No Ethernet frames originated from the guest during the observed boot period.

This makes a host-side DHCP failure significantly less likely. The investigation now moves to the guest boot process and the state of networking inside the Debian image.

## Finding - early guest reboot loop

**Status:** Confirmed

The repeated `Booting Debian GNU/Linux` message was not only a serial console artifact.

Libvirt events were monitored during a fresh VM start:

```bash
virsh -c qemu:///system event test-vm-wait \
  --all \
  --loop \
  --timestamp
```

The domain initially reported:

```text
Started Booted
```

but less than one second later started generating repeated reboot events.

During roughly 31 seconds of observation, 101 libvirt events were received, with reboot events repeating approximately every 0.6 seconds.

This confirms an early guest reboot loop.

It also explains the earlier networking symptoms:

- no guest-originated Ethernet traffic
- no DHCP request
- no DHCP lease
- no cloud-init logs
- no persistent userspace logs

For the KVM reboot loop, the network itself is not the primary suspect. That failure happens earlier in the guest boot chain.

## Hypothesis - Q35 machine type

**Status:** Rejected

The same Debian `generic` image was tested with the legacy `pc` machine type, which maps to `pc-i440fx-10.0` on this host.

The result did not change.

The guest continued generating repeated reboot events approximately every 0.57 seconds.

This means the reboot loop is not specific to the Q35 machine model.

## Hypothesis - host-passthrough CPU mode

**Status:** Rejected

The VM was recreated using libvirt `host-model` instead of `host-passthrough`.

On this host, `host-model` resolves to:

```text
Skylake-Client-IBRS
```

The behavior did not change.

The guest entered the same early reboot loop, with the first reboot occurring less than one second after startup.

The CPU presentation mode is therefore unlikely to be the cause.

### Test setup issue - `qemu64` CPU model

An attempt to use `qemu64` as the common CPU model for the KVM vs TCG comparison failed before the guest started:

```text
Host CPU does not provide required features: svm
```

The physical host uses an Intel CPU, while this `qemu64` configuration requires the AMD SVM virtualization feature.

This result is not related to the guest reboot loop because the VM never reached the boot stage.

A CPU model explicitly reported as usable by both KVM and TCG will be selected instead.

## Finding - KVM vs TCG

**Status:** Confirmed

A controlled comparison was performed using the same:

- Debian 13 `generic` image
- Q35 machine type
- `Nehalem` CPU model
- 1 vCPU
- 1 GiB RAM
- virtio disk
- virtio network interface
- cloud-init configuration

The only significant change was the virtualization backend.

### KVM

```text
virt-type: kvm
CPU:       Nehalem
```

Result:

- guest entered the previously observed reboot loop
- reboot events appeared approximately every 0.6 seconds

### TCG

```text
virt-type: qemu
CPU:       Nehalem
```

Result:

- domain remained running (booted)
- no reboot events were observed during the monitoring period

### TCG reset test

A later `virsh reset` caused the TCG domain to shut down.

This was initially suspicious, but the QEMU log showed that the process was explicitly terminated by `libvirtd` with SIGTERM.

The VM had been created through the first-boot `virt-install --cloud-init` workflow, which uses special reboot behavior during the temporary installation phase.

This shutdown is therefore considered a test lifecycle artifact, not evidence of the original guest reboot loop.

The earlier KVM vs TCG result remains valid:

- KVM generated repeated guest reboot events
- TCG remained stable without reboot events

This strongly isolates the early reboot loop to the KVM / hardware virtualization path.

The exact KVM-side root cause is still unknown.

### Exception trace result

The first KVM boot with `-no-reboot` successfully stopped the repeated reboot cycle after the first reset request.

QEMU tracing included:

```text
cpu_reset
int
guest_errors
trace:kvm_run_exit_system_event
```

The trace did not contain an exception cascade, double fault, triple fault, watchdog event or KVM internal error.

Two CPU Reset state dumps were present, including the standard x86 reset-vector state (`CS=f000`, `EIP=fff0`), but these dumps alone do not identify the source of the reset.

The triple-fault hypothesis is therefore not confirmed.

At that point, the next diagnostic step would have been to trace the actual reset request path.

The TCG guest has not yet received a DHCP lease, so successful guest boot and networking are not confirmed yet.

## Investigation outcome

The exact KVM-side root cause was not identified.

The investigation was paused because the project direction changed from a plain Debian + libvirt host to Proxmox VE.

This troubleshooting record is intentionally kept because it documents:

- the observed failure,
- hypotheses that were tested and rejected,
- the KVM vs TCG comparison,
- the point at which the failure was isolated to the KVM / hardware virtualization path.

The issue should not be considered technically resolved. The investigation was superseded by a platform architecture decision.

## Notes

The `bridge` command was also not available in the current shell when running:

```bash
bridge link show master virbr50
```

This is a separate tooling/path observation and is not currently considered the cause of the DHCP problem.

`tcpdump` was not installed on the host initially. Version 4.99.5 was installed to inspect DHCP traffic directly on `virbr50`.

## Fix

No fix was applied.

The underlying KVM issue remains unresolved because the investigation was intentionally stopped after the platform architecture changed.

## Verification

Not applicable.

The original failure was not resolved or re-tested after the platform direction changed.

## Lesson learned

The investigation showed that the original DHCP symptom was misleading.

The network stack became the first suspect, but packet captures and VM lifecycle testing showed that the guest was failing earlier in the boot process.

The KVM vs TCG comparison was the most useful test because it isolated the failure to the hardware virtualization path without pretending that the exact root cause had been identified.

The broader lesson is simple: validate the lowest failing layer before spending more time debugging services above it.
